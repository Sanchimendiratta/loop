# Loop Lite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Loop Lite — eight screens, three sheets, no email — as the launchable subset of the v1.3 Loop build, on branch `feat/loop-lite`.

**Architecture:** Branch from `main`'s full v1.3 build (48 commits, 209 tests), prune what Lite drops, reshape the board into a table and verification into a form, then add three new surfaces (My applications, My posts, the bell). Six of twelve core modules survive because they carry fix rounds worth keeping; the rest are deleted. The store stays the single repository boundary and still enforces D2.

**Tech Stack:** React 19, TypeScript (strict), Tailwind 4, Vite 8, Vitest. No backend — `localStorage` only.

**Spec:** `docs/superpowers/specs/2026-09-17-loop-lite-design.md`

## Global Constraints

- **Node >= 20.** ESM package.
- **No network at runtime.** No email, no LLM, no scraping. A pasted LinkedIn URL is text that is never fetched, embedded or previewed (§6 screen 8, §7.1 rule 5).
- **`src/core/` imports nothing** outside itself and `src/data/schema.ts`.
- **No `src/ui/` module may call `store.getState()`, touch `localStorage`, or import `src/core/privacy.ts`** (which is deleted in Task 1). The smoke script fails the build on any of these.
- **No UI module filters by viewer.** Every store read is viewer-scoped.
- **D2 is non-negotiable:** an unverified or pending member reads nothing — not posts, not members, not counts (§7 rule 1).
- **Applicant details reach exactly one person** — the poster of the post applied to. Enforced in the store, never in a component (§7.1 rule 1).
- **No disclosure by surprise:** before Apply is confirmed, the member sees every field the poster will see (§7.1 rule 2).
- **The contact route is absent from the DOM until Apply** — not hidden with CSS (§7.1 rule 5).
- **Lite has eight screens.** If a screen is not in §6, it is not in this build.
- **Plain tables, no cards, no infinite scroll** (§10). Friendly means well-made: real `<table>` semantics with `<th scope>`, `aria-sort` on sort controls, tabular numerals, plain-language status labels, inline failures next to the control, and a stacked mobile layout at 390px.
- **Status changes commit immediately** — no save button, no modal, no reload (§6 sheet 2).
- **Every commit** runs `npm run verify` before it is made.

```ts
/**
 * The connection field, and the one line it produces (Lite §4 field 7).
 *
 * v1.3 composed this from rung × destination across twenty combinations. Lite
 * drops `destination_type` entirely, so the sentence collapses to the rung
 * alone — four lines, written out. The `forwarded` line stays blunt on purpose:
 * it is what lets a candidate decide in two seconds whether to spend an hour.
 */
import type { Connection } from '../data/schema.ts';

export const CONNECTION_RANK: Record<Connection, number> = {
  hiring: 1,
  works_here: 2,
  knows_contact: 3,
  forwarded: 4,
};

const BADGE: Record<Connection, string> = {
  hiring: "I'm hiring",
  works_here: 'Works here',
  knows_contact: 'Knows the contact',
  forwarded: 'Just passing it on',
};

export function connectionBadge(c: Connection): string {
  return BADGE[c];
}

export function connectionLine(c: Connection, posterName: string, contactName: string | null): string {
  switch (c) {
    case 'hiring':
      return `${posterName} is hiring for this role.`;
    case 'works_here':
      return `${posterName} works here and can refer you.`;
    case 'knows_contact':
      return contactName
        ? `${posterName} doesn't work here but knows ${contactName}, the hiring contact.`
        : `${posterName} doesn't work here but knows the hiring contact.`;
    case 'forwarded':
      return `${posterName} has no connection — this is a cold application.`;
  }
}
```

`src/core/freshness.ts` — replace the file:

```ts
/**
 * Post ageing (Lite §6 sheet 3).
 *
 * v1.3 ran a confirm-or-decay clock with prompts at day 14 and 28 and an
 * auto-archive at 45. Lite keeps only the visible half: a post with no update
 * in 30 days greys out and drops to the bottom. Nothing is hidden, and there is
 * deliberately no `shouldArchive` — a poster who never returns should see their
 * post fade, not vanish.
 */
import { daysBetween } from './time.ts';

export const STALE_AFTER_DAYS = 30;

export function postAge(post: { postedAt: number }, now: number): { ageDays: number; stale: boolean; label: string } {
  const ageDays = daysBetween(post.postedAt, now);
  return {
    ageDays,
    stale: ageDays >= STALE_AFTER_DAYS,
    label: ageDays === 0 ? 'today' : `${ageDays}d ago`,
  };
}
```

```ts
/**
 * Board ordering (Lite §6): connection rung, then newest.
 *
 * Lite drops v1.3's freshness tier from the sort key — a stale post sinks
 * because it is older, not because a separate rule demotes it, and nothing is
 * filtered off the board at all.
 */
import { CONNECTION_RANK } from './disclosure.ts';
import type { JobPost } from '../data/schema.ts';

export function sortPosts(posts: JobPost[], _now: number, mode: 'connection' | 'recent' = 'connection'): JobPost[] {
  return [...posts].sort((a, b) =>
    mode === 'recent'
      ? b.postedAt - a.postedAt
      : CONNECTION_RANK[a.connection] - CONNECTION_RANK[b.connection] || b.postedAt - a.postedAt,
  );
}
```

```ts
/**
 * The application status ladder, and Lite's only nudge (§6 sheet 2).
 *
 * v1.3 had a nudge engine that chased whoever owed an update by email. Lite has
 * no email and no engine: a row untouched for 14 days shows a soft amber dot
 * and the sheet header says how many. "The sheet nags gently by looking
 * incomplete." Nothing blocks, nothing penalises.
 *
 * A terminal status is never stale — the ladder has ended, so there is nothing
 * left for the member to tell us, and dotting it would be nagging about
 * something already finished.
 */
import { daysBetween } from './time.ts';
import { TERMINAL_APPLICATION_STATUSES } from '../data/schema.ts';
import type { Application, ApplicationStatus } from '../data/schema.ts';

export const STALE_APPLICATION_DAYS = 14;

export const STATUS_LABEL: Record<ApplicationStatus, string> = {
  yet_to_respond: 'Yet to respond',
  in_review: 'In review',
  interview_scheduled: 'Interview scheduled',
  awaiting_next_round: 'Awaiting next round',
  offer: 'Offer',
  rejected: 'Rejected',
  no_response: 'No response',
};

export function isStale(a: Application, now: number): boolean {
  if (TERMINAL_APPLICATION_STATUSES.includes(a.status)) return false;
  return daysBetween(a.statusUpdatedAt, now) >= STALE_APPLICATION_DAYS;
}

export function staleCount(apps: Application[], now: number): number {
  return apps.filter((a) => isStale(a, now)).length;
}

export function staleNotice(n: number): string | null {
  if (n <= 0) return null;
  return n === 1
    ? "1 application hasn't been updated in a while."
    : `${n} applications haven't been updated in a while.`;
}
```

```ts
/**
 * The three events that generate a bell item (§5).
 *
 * Exactly three, deliberately: someone applied to your post, you were verified,
 * a post you applied to was marked filled. Every one is something that happened
 * to the member rather than something the product wants from them.
 */
import type { Notification, NotificationKind } from '../data/schema.ts';

export function notificationBody(
  kind: NotificationKind,
  ctx: { actorName?: string; roleTitle?: string },
): string {
  const role = ctx.roleTitle ?? 'your post';
  switch (kind) {
    case 'applied_to_your_post':
      return ctx.actorName ? `${ctx.actorName} applied to ${role}.` : `Someone applied to ${role}.`;
    case 'you_were_verified':
      return "You're verified — welcome in.";
    case 'post_filled':
      return `${role} was marked filled.`;
  }
}

export function unreadCount(ns: Notification[]): number {
  return ns.filter((n) => n.readAt === null).length;
}
```
